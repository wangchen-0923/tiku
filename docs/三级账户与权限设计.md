# 三级账户与权限设计

> **结论**：三级账户不是"三档权限开关"，而是**三类互不隶属的主体**——
> 系统管理员拥有平台、学校平台账户拥有学校、教师拥有自己的教学产出。
> 权限设计的核心不是"能不能点这个按钮"，而是**这条数据归谁、谁能看见、谁能改**。

- 版本：v1.1｜2026-10-21 19:45
- 适用：zhifou 后端 17 个 app、前端全部路由
- 状态：**P0/P1 已落地，P2 部分落地**（见第八节）

---

## 一、三级账户怎么分

| 级别 | 名称 | 系统内 `role` 值 | 归属 | 数量 | 典型持有人 |
|---|---|---|---|---|---|
| L3 | 系统管理员 | `PLATFORM_ADMIN` | 平台（`org` 为空） | 1–3 个 | 我方运营 / 实施负责人 |
| L2 | 学校平台账户 | `ORG_ADMIN` | 单校（`org` 必填） | 每校 1 主 + 1 备 | 信息中心 / 教务主任 |
| L1 | 教师账户 | `TEACHER` | 单校（`org` 必填） | 不限 | 任课教师 |
| — | 学生身份行 | `STUDENT` | 单校（`org` 必填） | 每学号 1 个 | 不是账户，不进三级 |

> **【图 1】三级账户层级**（待出图：三层金字塔。顶端"系统管理员"旁标注"org 为空｜1–3 人"，
> 中层"学校平台账户"旁标注"每校 1 主 1 备"，底层"教师账户"横排多个；
> 右侧竖排灰色虚线框标"学生身份行：无凭据、不登录、等级 0"）

**为什么保留 `PLATFORM_ADMIN` / `ORG_ADMIN` 这两个旧值、只改显示名**

后端 18 处视图判断、9 个回归脚本、前端 3 个文件都硬编码了这两个字符串。
改 DB 值要连带改数据、代码、脚本、前端四层，收益只是"名字好听"。
三个级别的**语义**已完全对应，所以：**值不动，显示名与文档术语统一为新三级**。

### 三个主体的本质区别

- **系统管理员**是"平台方"。他决定**有哪些学校存在**、每家能用多少、什么内容可以进公共库。
  他不教任何一个班，所以**不该看见任何一个学生的成绩**。
- **学校平台账户**不是"权限更高的老师"，而是**学校在平台上的法人代表**。
  服务额度、协议、账单、数据归属都绑在它身上。它管的是"这片数据"，不是"这门课"。
- **教师账户**是"在平台上干活的人"。他拥有**自己产出的东西**：自己出的题、自己组的卷、自己布置的作业。

这三者之间没有上下班的汇报关系，只有**授权关系**。所以不能做成"一个角色继承另一个角色的全部权限"，
否则会出现"系统管理员自动拥有全部教学权限"——那正是当前系统的状态，也是这次要拆掉的东西。

## 二、真正的权限是"数据圈"

角色只回答"你能不能调这个接口"。**看得到多少数据**由另一套东西决定，我称之为作用域（scope）：

| Scope | 名称 | 谁拥有 | 含义 |
|---|---|---|---|
| `PLATFORM` | 平台视图 | 系统管理员 | 跨校**聚合**：学校数、活跃教师数、题库健康度、AI 用量。**不含姓名、成绩明细、试卷内容** |
| `ORG_ALL` | 全校 | 学校平台账户 | 本校全部数据，含所有班级、所有教师产出 |
| `OWN_TEACHING` | 所教范围 | 教师 | 自己创建的内容 + 自己任教的班级 |
| `SELF` | 本人 | 所有登录账号 | 个人中心、自己的操作日志、自己的积分 |

> **【图 2】数据圈四层同心圆**（待出图：由外到内 PLATFORM / ORG_ALL / OWN_TEACHING / SELF，
> 每层右侧标注典型查询，如"PLATFORM：各校题量分布"、"OWN_TEACHING：我教的 3 个班"）

**当前系统的教师作用域是错的。** 后端所有列表接口都走 `_org_id(request)` 取 `user.org_id`，
于是**任何一个教师都能看到全校所有班级的成绩**。一所 60 个班、120 名教师的学校，
新入职的老师登录后能看到全校三年的学情——这不是权限设计，是没设计。

但一次性收窄会打断现有流程，所以**分两步**（见第六节 P1/P2）：

1. **先收窄敏感数据**：成绩明细、学生档案、学情报告 → 严格 `OWN_TEACHING`；
2. **试卷与题库保持校内可见**：教师之间本来就要互相借卷、复用题，收窄反而伤业务。

## 四、六条铁律

### 铁律 1 · 只能管低一级

任何写角色的操作，要求 `rank(目标) < rank(操作者)`。

- 学校平台账户只能建教师、只能改教师；**不能建第二个学校平台账户**（防止校内出现两个平级账号互相锁死）。
- 建第二个学校平台账户是**系统管理员**的动作（开校时一并做，或事后补设备用账号）。
- **同级不可互改**的唯一例外是系统管理员：多个 sysadmin 之间允许互相恢复，
  否则唯一一个 sysadmin 密码丢了就整站失守。

### 铁律 2 · 不跳级授权

学校平台账户**不能**创建任何高于教师角色的账号。当前的
`UserService._check_role_ceiling()` 已实现这条，但只做了一半——它没有拦"同级"。

### 铁律 3 · 不能改自己

不能改自己的角色、不能停用自己、不能删自己。
一条命令把自己降成教师、或者停用，会导致该校**再没有人能恢复它**。

### 铁律 4 · 平台不碰教学

系统管理员对成绩、试卷、名册、作答**只有聚合读，无写**。
当前代码的注释已经写了这个意图（"平台管理员也要求带机构才能操作业务数据"），
但**没有真正拦住**——见第五节第 2 条。

### 铁律 5 · 角色实时生效，机构变更强制重登

`JWTAuthentication` 每次请求都从库里加载 user，所以**改角色立即生效**，不需要等令牌过期。
机构变更则会使旧令牌失效（`org_id` 与令牌声明不一致即拒绝）。这两条现有实现是正确的，保留。

### 铁律 6 · 撤销权必须留给学校

教师会离职。如果试卷、题库、知识库条目只归教师个人，人一走数据就成孤儿。
所以**学校平台账户必须能接管、移交本校任何教师的数据**——
这条比"能建账号"更关键，它是 L2 存在的真正理由。
当前系统**没有这个能力**（没有任何 transfer / 接管接口）。

## 五、现状与差距

以下全部来自当前 PG 库（`zhifou`，2026-10-21 19:00）与代码实测：

| # | 现状 | 问题 |
|---|---|---|
| 1 | 全库仅 **1 所机构**（`id=1 测试学校`） | 跨校隔离逻辑从未被真实多校场景验证 |

| 3 | `ORG_ADMIN` 账号 **0 个** | 二级账户从未真正存在，学校层面无人管 |

| 6 | 前端 `router.beforeEach` **只判登录态，0 处角色/能力判断** | 教师直接输地址就能进管理页。后端虽会 403，但页面白屏、错误提示不友好 |
| 7 | 教师列表接口一律 `filter(org_id=...)` | 教师能看到全校成绩（第二节已述） |

> 第 2 条是这次设计要动的第一刀：**把 `admin` 拆成两个账号**。
> 不拆的话，后面所有权限规则都形同虚设——因为总有一个人能绕过它们。

## 七、数据迁移与验收

### 迁移（必须在一个事务里）

```sql
-- 1) 把现存的"平台管理员"降为学校平台账户
UPDATE "user" SET role='ORG_ADMIN', is_superuser=false, is_staff=false
WHERE username='admin';

-- 2) 新建真正的系统管理员（org 为空）
--    由脚本创建，不在此写明文密码
--    role='PLATFORM_ADMIN', org_id=NULL, is_superuser=true, is_staff=true

-- 3) 断言：此后不允许再出现"平台管理员带机构"
ALTER TABLE "user" ADD CONSTRAINT ck_platform_admin_no_org
  CHECK (role <> 'PLATFORM_ADMIN' OR org_id IS NULL);
```

第 3 步的约束是关键：它把一条**口头规则**变成**数据库拒绝**。
现状那条 `admin(org_id=1)` 正是因为规则只写在注释里，才活了这么久。

### 验收（16 条，全部跑在 PG 上）

| 组 | 用例 |
|---|---|
| 建号 | 学校账户建教师 ✅；建第二个学校账户 ❌403；建系统管理员 ❌403；教师建任何账号 ❌403 |
| 改角色 | 学校账户把教师提为学校账户 ❌403；把自己降级 ❌403；系统管理员改自己 ❌403 |

| 移交 | 学校账户把离职教师 3 份试卷移交后，接收人可见、原账号停用后数据不丢 |

| 教师查成绩列表 | 200，返回全校 **531 条** | 200，返回 `[]`（只给所教班） |
| 教师看别班详情/名册 | 200，看到全班姓名学号 | **403**「你不在该班级任教」 |
| 教师看别班作业花名册 | 200 | **403**「你不在该作业任教」 |
| 系统管理员查成绩 | 200（跨校） | **403**「只能看汇总，不能看明细」 |
| 教师在自己当班主任的班 | — | 200（正向放行已验证） |

### 8.4 未做的两项（P2 剩余）

1. **越权被拒写审计**：目前拒绝只返回 403，不落 `audit_log`。
   做的话要评估日志量（一个老师反复点错菜单会产生大量记录），
   建议只记「跨班/跨校访问」这类高风险拒绝。
2. **`/api/v1/platform/` 命名空间**：现平台接口仍在 `/org/orgs/`、
   `/accounts/users/` 下，靠角色判断区分。纯重构，无功能收益，可延后。

### 8.5 已知数据模型缺口

系统里**没有「任教关系」表**。教师「所教班级」目前由两个来源推断：
`Classroom.head_teacher`（班主任）+ 他创建过作业的班。
副作用：老师**第一次**给某个班布置作业之前，看不到那个班的成绩。

这是保守方向（宁可看不到，不可多看），但正确解法是补一张
`classroom_teacher` 任教关系表，归入后续批次。

## 九、v1.2 规则改版：班级归教师个人（2026-10-21 晚）

> **业务方定稿的一句话**：学校不统一设置班级，只授权教师账号；
> 班级由教师自行设置；教师只能看到自己的数据。

这一句把 v1.1 的两处**核心假设**推翻了，必须单独记录，否则后来的人
会照着 v1.1 的旧口径去改代码。

### 9.1 推翻的两条旧口径

| 项 | v1.1 | v1.2（现行） |
|---|---|---|
| 谁建班 | 学校平台账户（`require_school_admin`） | **教师自己**，`owner` 自动记为自己 |
| 班级唯一键 | `(org, name, academic_year)` 全校唯一 | `(org, owner, name, academic_year)` **按人唯一** |
| 教师看哪个班 | 「班主任的班 ∪ 布置过作业的班」**推断** | `owner = 自己`（或学校指派他为班主任）**事实** |
| 试卷/题库 | 刻意**校内共享**（理由是「老师要借卷」） | 自己的 + **学校建的公共内容**；同事个人的看不到 |

★ 唯一键那一行是这次改版里最容易被漏的：
  沿用全校唯一的话，第二位老师建「机械1班」会被拒绝，
  而他在自己列表里看不到那个班，**根本无从理解为什么被拒**。

### 9.2 「自己的」怎么界定（三档）

| 数据 | 教师可见范围 | 理由 |
|---|---|---|
| 班级 / 名册 / 成绩 / 学情 / 作业 | 只有自己的 | 含学生姓名与成绩，最敏感 |
| 试卷 / 题目 / 知识条目 | 自己的 + **学校账户建的** + 无主的 | 学校统一采购/导入的是公共资源，教师第一天就要能用 |
| 答题卡模板 | 自己的 + **已发布**的 + 无主的 | 模板是**工具**不是内容；每人重画一张 40 题卡没有意义 |

★ 「学校账户建的 = 公共的」这一层是**必须的**，不是偷懒：
  库里 1900+ 道题、几十张卷都是学校账户导入的。纯按 `created_by`
  收窄，教师登录后题库直接是空的 —— 而那正是他最该用的资源。
  判据用创建者的**当前角色**（`public_owner_ids()`），不是建库时的快照。

### 9.3 实现落点

### 9.4 一个容易被忽略的坑

**「PATCH 里出现了 `owner_id` 就 403」，不是「值变了才 403」。**

教师编辑自己的班时，表单会把回填的 `owner_id` 原样带回。后端看到
请求体里有这个键就拒绝 —— 于是老师改个班名也 403。前端 `save()` 里
必须显式 `delete payload.owner_id`，不能靠「值没变」来规避。
