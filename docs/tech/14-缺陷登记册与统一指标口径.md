## 一、P0 严重缺陷（已修）

这四条若不修，会造成**防线失效**或**迁移失败**，属于必须在开工前解决的类型。

### D-01 ✅ 锚点质量分公式量纲错误，防线等于没有

| 项 | 内容 |
| --- | --- |
| 位置 | 设计文档 9.3.2 ③ `rectify_and_validate` |
| 原文 | `quality = 1.0 - contourArea(anchors) / (dst_w * dst_h)` |
| 问题 | `anchors` 坐标在**原图**像素坐标系，`dst_w × dst_h` 是**校正后**图像像素面积，两者尺度不同；且四锚点凸包面积通常远小于整页面积 → 该值**恒在 0.99 附近，完全不具判别力** |
| 后果 | 9.3.2 明确称这是「防止整卡识别出全错答案的关键防线」——**实际这条防线不存在**。锚点误检（例如把印刷边框角当锚点）不会被拦截，可能输出一整张看似正常但完全错误的答案 |
| 修复 | 改为**以回投影偏差为主（权重 0.55）** + 锚点形状（0.25）+ 锚点数（0.10）+ 实心度（0.10）的加权质量分；偏差归一化为「相对页面宽度的比例」以便与 `omr.anchor_max_deviation`（0.01）直接比较 |
| 修复位置 | 设计文档 9.3.2 ③（已补修正记录）；实现细节见 [08-答题卡与OMR规格.md](08-答题卡与OMR规格.md) 4.5 节 `anchor_quality_score()` |
| 新增阈值 | `omr.anchor_quality_min` = 0.6（**需在阶段零用真实样本标定**）→ 见 [13-配置项与提示词库.md](13-配置项与提示词库.md) 五节 |
| 状态 | **已修**（2026-10-01） |

| --- | --- |
| 位置 | 设计文档 7.4.8.6 给 `question_image` 新增的字段清单 |

### 2.2 ★ 统一口径（**以下为唯一权威值**）

**分三个语义层次，命名必须区分，不得混用**：

| 层次 | 定义 | 用途 |
| --- | --- | --- |
| **G（Gate）** | 阶段零 Go/No-Go 阈值 | 决定是否按当前方案继续，**低于此值触发产品形态调整** |
| **A（Acceptance）** | 阶段一验收阈值（一期必须达标） | **正式验收依据**，对应 19.1 的 A 编号 |
| **T（Target）** | 阶段二优化目标（达标是加分，不达标不阻断一期验收） | 阶段二的努力方向 |

#### 2.2.3 ★ 「沉默错误率」口径作废，改为两个可测指标

**问题**：v2.0 的 A7 定义「沉默错误率 = 教师未发现而确认入库的错误图 / 总错误图 ≤ 2%」。这条在 v2.1 下**双重失效**：

| 失效原因 | 说明 |
| --- | --- |
| ① 与零容忍冲突 | v2.1 已改为「强制逐图确认」（Q4），错误图不可能未经教师过目就入库，容忍 2% 自相矛盾 |
| ② **结构性测不到「丢失图」** | 丢失的图**不产生 `question_image` 记录** → 界面上没有 `PENDING` → **教师不可能发现它** → 它进不了分子（教师发现数）却进得了分母（ground truth 总错误数）→ **该指标恒偏高且不可归因** |

**替代方案（两个可测指标）**：

| 新指标 | 定义 | 测法 | A（一期验收） |
| --- | --- | --- | --- |
| **最终入库错误率** | 已入库配图中存在错误的图数 / 已入库配图总数 | **可自动统计**：人工对入库结果做抽样核对（每批抽 20%） | **= 0**（零容忍） |
| **SER_可发现** | 裁切错 + 归属错的错误图中，教师确认环节漏掉的比例 | 3 位教师正常校对 20 份 → 另 1 人逐题核对（这些错误**在界面上可见**，所以可测） | ≤ 1% |
| **SER_不可发现** | 丢失图的比例 | **不使用教师实验**，直接用**配图召回率**衡量（丢失图 = 召回失败） | 见 2.2.2 召回率 |

> **责任划分**：可发现的错误由「确认环节」负责，不可发现的错误（丢图）由「召回率」负责。**这样每个错误都有明确的度量归属，不会出现「没人负责」的指标。**

   全可见又变成同事互相监控。
2. **作答不开 `PATCH`**：写入只走学生提交 / 扫描回写 / 教师录分三条正式通道，
   它们各带时间窗、乱序还原、来源优先级与审计。开一个直改口子等于绕开全部守卫。
3. **`merge` 幂等且只在实际变更时写审计**：每次点击都记一条会把真正那次变更埋掉。

★★ 通用教训（V-37）：**「字符串码 + 枚举」的组合是最容易漂移的一对**。
`CharField(choices=...)` 在 DB 层**不产生任何约束**，所以「写了不在 choices 里的值」
永远不会报错。凡这种设计，都必须配一条**扫描源码**的测试，
而不是靠人记得「加新动作时要同步改枚举」。
同类前例：`omr` 的任务名与 `CELERY_TASK_ROUTES` 键对不上（V-33），
同样是「字符串当标识、两边各写一份、对不上不报错」。

★ 一条脚本层面的经验（非产品缺陷）：**删除自引用 SET_NULL 的链式表不能用 `QuerySet.delete()`**。
Django 收集器会**先** `UPDATE ... SET superseded_by_id=NULL WHERE superseded_by_id IN (待删)`，
**再**删行；于是「A→B」删 B 的那一刻 A 变 NULL 而 B 仍是 NULL，同一 `(任务,学生,卷面题)`
出现两条 NULL → 撞部分唯一索引。逐条倒序删同样躲不开（置 NULL 在删除之前）。
清理脚本要用 `QuerySet._raw_delete()` 一条 `DELETE ... IN (...)` 走完。
