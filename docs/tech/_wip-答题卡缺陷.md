## D2 / D4 · 「一行多组」没生效，整块被推下去 —— ✅ 已修（第 8 轮）

### 现象

```
左列： 1 2 3 4 5
右列： 6 7 8 9 10     ← 但 y 比左列低 6 行，看起来串到下一题型
```

### 定位（坐标是决定性的）

修复前的实测坐标：

```
左列 1–5 ：x=27.92   y=101.29 → 121.46
右列 6–10：x=108.00  y=131.54 → 151.71   ← 比左列低 6 行
```

修复后：

```
组 1（题 1–5）： x=27.92   y=101.29 → 121.46
组 2（题 6–10）：x=108.00  y=101.29 → 121.46   ← **同一 y 区间**
```

### 两个真根因（都在渲染器，layout 侧一直是对的）

**① `y` 累加写在了「组」循环里**

`layout.iter_bands()` 的语义是两级：

| 层级 | 含义 | 排布方向 |
| --- | --- | --- |
| **组块（band）** | 一行并排的若干组 | 沿 **y** 依次排 |
| **组（group）** | 组块内的列 | **同一 y**，x 递增 |

而渲染器把 `y += GROUP_SIZE * row_pitch + row_pitch` 写在了**组循环**里 ——
一个组块有 2 个组就加 **2 次**，于是第 2 组被推下去 6 行。

★ 修法：累加移到**组块循环**，且只累加到 `band_y`（组内不偏移）。

**② 列宽按 `columns` 平均，而不是按「本组块实际的组数」**

`columns` 是「一行**最多**放几组」。实测 `count=10 / columns=4`
时 `iter_bands` 只给 **2 个组**，但渲染按 4 列分宽 ——
第 2 组被推到第 3 列的位置（x=108 而非 93.5）。

★ 修法：`band_w = cw / len(band)`。题多时 `len(band) == columns`，行为不变。

★★ 这两处都是同一类错误：**渲染器自己又算了一遍 layout 已经算好的几何**。
本项目到目前为止这类错误已出现 **10 次**。

## D3 · 大题边框穿过下一个题型标题 —— ✅ 已修（第 7 轮）

### 定位（坐标证据）

新增诊断工具 `scripts/diag_pdf_rects.py`（打印 PDF 里的**矩形**坐标，
与 `diag_pdf_text_pos.py` 的文字坐标对照）。实测：

```
「一、单项选择题」框          y 116.66–210.00
「二、判断题」标题（实际位置）  y ≈ 213.5（由首行 219.90 − 1.6×行距 推得）
```

★ 框底 210.00 越过了自己该管的区间。

### 三次尝试（前两次**没修好**，都记下来）

| 尝试 | 做法 | 结果 |
| --- | --- | --- |
| ① | 夹到「下一个分节的**首行** y」（219.90） | ❌ `min(210.00, 219.40)` 取不到它，**等于没夹** |
| ② | 夹到「下一个分节的**标题起点**」（219.90 − 6.4 = 213.50） | ✅ 真实模板框底 **210.00 → 207.99** |
| ③ | 框底改用 `box_h_mm` + 0.6，留白 1.2mm | ✅ 真实模板仍 207.99，合成用例也稳定 |

★ 教训一：**夹取的目标要选「下一个元素真正占用的上边界」**。
选首行 y 会白占 6.4mm 的标题高度，看起来像「没生效」。

★ 教训二：**候选必须过滤掉「落在自己之前」的**。
主观题区的 `y_top` 可能在别的页或已排完，直接参与 `min` 会取到一个
比 `top` 还小的值 → `next_y > top` 不成立 → **整条夹取被跳过**。
（这正是合成用例一直红的原因。）

★ 教训三：**判定「压字」要看相交深度，不是中心点。**
我最初用「标题中心是否落在框内」，于是「框底 156.65 / 标题 155.12–158.91」
只报了一半真相。

### 实现

`SheetRenderer.draw_section()` 新增 `next_y_mm` 参数；调用方按
「本页本大题之后的第一个内容」算出它（下一个分节的标题起点，
或主观题区的 `y_top_mm`，取小者，**且只取落在自己之后的**）。

## D2 / D4 · 「一行 4 组」没实现，整块被塞进一列（待办）

### 现象（150dpi 实测）

```
左列： 1 2 3 4 5          ← 5 行
右列： 6 7 8 9 10         ← 也是 5 行，且每组 4 个框
```

期望（样例版式）：**一行 4 组题**，
每组 = 「题号 + 4 个涂点框」，即 `1 [A][B][C][D]  6 [A][B][C][D] …`。

### 已定位的方向

「4 列」是**题内选项的 4 个涂点框**，不是「一行 4 组题」。
`draw_section` 里 `per_group_w = cw / columns` 与
`iter_bands(len(seqs), columns)` 的 `columns` 语义需要核对：
它应当表示**一行放几组题**，而不是题内选项数。

★ 修法：核对 `layout.section_rows()` / `iter_bands()` 的 `columns`
口径，使「一行 4 组」成立，且**排版的组数与渲染的组数一致**
（这正是本项目反复出错的「量一次、画一次口径不同」）。

## D1 · 预览弹窗空白 —— ✅ 已修

### 现象与定位

需求方反馈：「有弹窗，是空白，最下方有文字提示」。
**Console 无任何报错。**

我逐层排查后确认：

| 检查 | 结果 |
| --- | --- |
| `GET /sheet/templates/{id}/pdf/` | ✅ HTTP 200 + 合法 `%PDF`（6181 字节） |
| 前端是否发出请求 | ✅ 发出且成功（否则 `openPdf` 会走 catch 弹错） |
| Console 报错 | ❌ 无 |
| iframe 渲染 | **❌ 空白** |

→ 结论：**Chrome 内置 PDF 查看器在 `blob:` URL + `<iframe>` 下静默失败**。
请求成功、字节正确、没有任何错误信号，但就是不出图。

★ 这也是「无报错」本身就是线索的一次：
**没有报错 ≠ 没有问题** —— 内嵌 PDF 是浏览器**原生渲染**，
它失败时不走 JS 异常通道。

### 修法（三重保险，不引入新依赖）

★ **不能装 `pdfjs-dist`**：本机 DNS 已失效（见 `04-部署与运维手册`），
`pnpm add` 会拉不到包。

1. **`<object type="application/pdf">` 优先于 `<iframe>`**
   `object` 在**内嵌渲染失败时会走 fallback 内容** ——
   我们才有地方放「在新标签页打开」这个出口。
   `iframe` 失败时是一片空白，**什么都放不了**。
2. **「在新标签页打开」按钮**（对话框底部 + fallback 里各一个）
   新标签页是**顶层文档**，PDF 查看器在那里正常工作。
   ★ 不绕开认证：仍是先用**已认证的 fetch** 取回 Blob，
     再把 `blob:` URL 交给新标签页 —— token 不进 URL、不进历史记录。
3. **兜底文案**：明确告诉老师「这是 Chrome 对 `blob:` 的限制，
   **不是文件坏了**」—— 否则他会以为系统出错。

### 新增 API

`web/src/api/sheet.ts` 加 `openBlobInNewTab(blob)`：
· 返回 `false` 表示被**弹窗拦截**（调用方提示老师允许弹窗）
· **不 `revokeObjectURL`** —— 新标签页要靠这个 URL 加载，
  回收它会让新标签页变空白

### 验证

- 前端 `typecheck` ✅ + `build` ✅ + 令牌四节 ✅
- ★ **需要人工在浏览器里确认**：点「预览」→ 若弹窗内嵌显示则直接可用；
  若空白则用「在新标签页打开」。**两条路都必须有一条能出图。**
