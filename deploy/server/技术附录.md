## 0. 这套东西是干什么的

学校的服务器系统是 OpenCloudOS 9，它自带的 Python 版本太旧（3.9 / 3.11），
而知否要求 Python 3.12 以上。手工升级系统 Python 很容易把服务器自带的软件搞坏。

解决办法是**容器化**：把 Python 3.12 和所有依赖打进一个"盒子"里运行，
和服务器系统完全隔离。本文描述的就是这个盒子的做法。

**你需要准备的三样东西：**

| 项目 | 说明 |
|---|---|
| 一台服务器 | 4 核 4G 以上，OpenCloudOS 9 / CentOS / Ubuntu 都行 |
| Docker | 服务器上的容器运行环境（安装见第 1 步） |
| 一个域名（可选） | 没有域名也能用公网 IP 访问，只是浏览器会提示"不安全" |

## 1. 服务器上安装 Docker（只需做一次）

复制粘贴执行（OpenCloudOS / CentOS）：

```bash
curl -fsSL https://get.docker.com | bash
systemctl enable --now docker
docker --version
```

看到 `Docker version 2x.x.x` 就成功了。

**★ 还必须确认是 Compose V2（这一步不做，后面一定会报错）**：

```bash
docker compose version
```

必须输出 `Docker Compose version v2.x.x`。

> ⚠ 如果输出是 `docker compose: command not found`，或者只有老的
> `docker-compose version 1.x.x`（**中间有横杠**），请**不要**继续：
> 老版本不认 `docker-compose.yml` 里的 `name:` 和
> `depends_on: ... condition: service_healthy`，会直接启动失败。
> 解决办法是装 Compose 插件：
> ```bash
> yum install -y docker-compose-plugin   # CentOS / OpenCloudOS
> apt-get install -y docker-compose-plugin  # Ubuntu / Debian
> ```
> 本文后面所有命令都写成 `docker compose`（**中间是空格，不是横杠**），
> 请你照抄时不要写回 `docker-compose`。

**如果 Docker 拉取镜像一直卡住或超时**（国内服务器很常见），配置镜像加速：

```bash
mkdir -p /etc/docker
cat > /etc/docker/daemon.json <<'EOF'
{
  "registry-mirrors": ["https://mirror.ccs.tencentyun.com"]
}
EOF
systemctl restart docker
```

> `mirror.ccs.tencentyun.com` 是腾讯云的公共加速地址。
> 如果你的服务器不是腾讯云，把它换成对应云厂商提供的加速地址。

## 2. 上传文件（最终目录长这样）

服务器上**固定**用 `/opt/zhifou` 作为部署根目录：

```
/opt/zhifou/
├── docker-compose.yml        ← 本文同目录的 docker-compose.yml
├── Dockerfile               ← 本文同目录的 Dockerfile
├── requirements.prod.txt    ← 本文同目录的 requirements.prod.txt
├── .dockerignore            ← 本文同目录的 dockerignore（上传后改名）
├── .env                     ← 本文同目录的 .env.prod.example（改名+填密钥）
├── server/                  ← ★ 把本机 D:\tiku\server 整个目录传上来
│   ├── manage.py
│   ├── apps/
│   └── zhifou/
│       └── settings/
│           └── serverprod.py   ← ★ 从 本文同目录/settings/ 复制过来
├── nginx/                   ← Nginx 配置（zhifou.conf / proxy_headers.conf）
├── staticfiles/             ← 自动生成（Django 静态文件，Nginx 从这里取）
├── media/                   ← 自动生成（老师上传的图片/文件）
└── backups/                 ← 数据库备份（运维脚本会用到）
```

> **关于端口**（这一条决定了网站能不能打开，别跳过）：
> - 后端容器把 8000 端口**只发布到服务器的 127.0.0.1**，公网访问不到
> - 宿主机 Nginx 用 `127.0.0.1:8000` 反代到它 —— 两边必须一致
> - PostgreSQL 和 Redis **一个端口都不对外**，连 127.0.0.1 都不监听

对应命令（在服务器上执行）：

```bash
mkdir -p /opt/zhifou/staticfiles /opt/zhifou/media /opt/zhifou/backups
cd /opt/zhifou
```

**上传方式**（任选一种）：

- **方式 A（推荐）**：用 WinSCP / FileZilla 等图形工具，把左边 Windows 的文件拖到右边服务器
- **方式 B**：在本机（Windows 的 Git Bash 或 PowerShell）用 scp：

```bash
# 上传本文所在目录的 4 个文件
scp D:/tiku/deploy/server/{docker-compose.yml,Dockerfile,requirements.prod.txt,dockerignore} root@你的服务器IP:/opt/zhifou/
# 上传后端源码整个目录
scp -r D:/tiku/server root@你的服务器IP:/opt/zhifou/
```

上传后在服务器上做**改名**和**放 settings**：

```bash
cd /opt/zhifou
mv dockerignore .dockerignore
mkdir -p server/zhifou/settings
# settings/serverprod.py 也要从本机 deploy/server/settings/ 传上来，放在：
#   /opt/zhifou/server/zhifou/settings/serverprod.py
```

> ⚠ **最容易出错的一步**：`server/` 目录里必须能看到 `manage.py`。
> 有些人用图形工具上传后会多一层目录，变成 `/opt/zhifou/server/server/manage.py`，
> 那样构建会失败。检查一下：
> ```bash
> ls /opt/zhifou/server/manage.py
> ```
> 能看到文件路径就对了。

## 3. 生成密钥并填好 `.env`

### 3.1 生成三个密钥

在你自己的电脑上执行（装了 Python 的话），或者在服务器上执行：

```bash
python -c "import secrets;print('ZF_SECRET_KEY      =', secrets.token_urlsafe(50))"
python -c "import secrets;print('POSTGRES_PASSWORD  =', secrets.token_urlsafe(24))"
python -c "import base64,os;print('ZF_PII_KEK         =', base64.b64encode(os.urandom(32)).decode())"
```

把输出的三行**保存好**（建议存到密码管理器）。

### 3.2 改名并编辑

```bash
cd /opt/zhifou
cp .env.prod.example .env
vi .env
```

> 不习惯 vi 的话，可以用 WinSCP 直接双击 `/opt/zhifou/.env` 编辑，保存即可。

**必须改的 5 项**（其它保持原样）：

| 变量 | 填什么 |
|---|---|
| `ZF_SECRET_KEY` | 3.1 生成的第一个值 |
| `ZF_ALLOWED_HOSTS` | 你的域名，没有域名就填公网 IP，如 `1.2.3.4` |
| `POSTGRES_PASSWORD` | 3.1 生成的第二个值 |
| `ZF_DB_PASSWORD` | **和 POSTGRES_PASSWORD 一模一样** |
| `ZF_PII_KEK` | 3.1 生成的第三个值 |

**填写时的三条铁律**（写错就会启动失败，且报错很难懂）：

1. 等号两边**不加空格**，写 `KEY=value`
2. 值**不加引号**，写 `KEY=abc`
3. 值里**不要有 `#` 和空格**

## 4. 构建镜像（★ 最慢的一步，请耐心）

```bash
cd /opt/zhifou
docker compose up -d --build
```

**预计 5～15 分钟。** 慢是正常的，因为要下载这几样大件：

- `rapidocr-onnxruntime` + `onnxruntime`：约 200MB（OCR 识别模型，随包自带）
- OpenCV、PyMuPDF、pandas 等

屏幕上会滚很多行英文，只要最后出现类似下面的内容就是成功了：

```
[+] Running 6/6
 ✔ Container zhifou_db             Healthy
 ✔ Container zhifou_redis          Healthy
 ✔ Container zhifou_web            Started
```

> ⚠ **中途不要按 Ctrl+C**。如果断了，重新执行同一条命令即可，
> Docker 会接着上次的进度继续（已下载的不会重下）。

## 5. 初始化数据库（只需做一次）

```bash
cd /opt/zhifou

# 建表（84 个迁移文件，约 1～3 分钟，会滚很多 OK）
docker compose exec web python manage.py migrate

# 收集后台管理页面的静态文件（Nginx 要靠它显示 /admin/ 的样式）
docker compose exec web python manage.py collectstatic --noinput

# 创建管理员账号（按提示输入用户名、邮箱、密码）
docker compose exec web python manage.py createsuperuser
```

## 6. 上传前端页面

前端要**在你自己的 Windows 电脑上**先打包，再上传：

```bash
# 在本机 D:\tiku\web 目录执行（需要装了 Node.js）
cd D:/tiku/web
npm install
npm run build
```

然后把生成的 `D:\tiku\web\dist` 整个目录上传到服务器的 `/www/wwwroot/zhifou/dist`。

```bash
# 服务器上先建目录
mkdir -p /www/wwwroot/zhifou
# 本机执行上传
scp -r D:/tiku/web/dist root@你的服务器IP:/www/wwwroot/zhifou/
```

> 容器里**没有** Node.js，前端必须在本地打好包再上传 —— 这是有意为之：
> 服务器只负责跑，不负责编译，镜像更小、更安全。

## 7. 检查是否成功

```bash
# 看 6 个服务是不是都在跑、是不是 healthy
docker compose ps

# 看后端日志的第一行，确认连的是 PostgreSQL 而不是 SQLite
docker compose logs web | head -20
```

**日志第一行长这样就对了**（这行是项目自带的自检输出，专门防止"以为连了 PG 实际连了 SQLite"）：

```
[ENV] DB=postgres:db:5432/zhifou | REDIS=redis://redis:6379/0 | MEDIA=/app/media
```

**在容器里直接探活**：

```bash
docker compose exec web curl -fsS http://127.0.0.1:8000/health/
```

返回 `{"status": "ok", ...}` 就说明后端活着。

### 7.1 六条必做的断言（★ 防「不报错的功能失效」）

下面这几项**配错了不会报错**，只会让系统在你看不见的地方悄悄降级。
部署完请各跑一次，输出对得上才算是真的部署好了。

**断言一：上传的文件必须落在卷上，而不是容器里**

```bash
docker compose exec web python -c "from apps.media.storage import get_backend; print(get_backend().root)"
```

- 正确输出：`/app/media`
- 错误输出：`/app/.zf-storage` ← **说明 `ZF_STORAGE_ROOT` 没生效**。
  后果：现在上传一切正常、预览也正常，但**重建容器后图片全没了**，
  而且备份脚本打出来的 media 永远是个空目录。

**断言二：重算任务必须真的投到队列**

```bash
docker compose exec web python -c "from apps.analytics.tasks import task_mode, is_queued; print(task_mode(), is_queued())"
```

- 正确输出：`queued True`
- 错误输出：`inline False` ← **说明 `ZF_TASK_MODE` 没生效**。
  后果：`worker_calc` 这个容器**永远空闲**，学情重算在网页请求里当场算，
  批改 / 统计接口会明显变慢，而日志里什么都看不出来。

**断言三（安全）：媒体文件不能被匿名下载**

学生答题卡照片里有姓名，只能走「登录 + 本机构校验」的接口取，
**不能**让 Nginx 直接把 `/opt/zhifou/media` 对外开放。验一遍：

```bash
# 找一个真实存在的**图片**（相对 /opt/zhifou/media 的路径）
# ★ 只挑图片：期望值稳定是 image/*，不会因为抽到一个 txt/pdf 而误判
REL=$(cd /opt/zhifou/media && \
      find . -type f \( -name '*.png' -o -name '*.jpg' -o -name '*.jpeg' \) \
      | head -1 | sed 's|^\./||')

# ★ 空集守卫：media 还是空目录时不能算「通过」，只能是「跳过」
if [ -z "$REL" ]; then
    echo "断言跳过：media 里还没有图片，请先上传一张配图再验（跳过 ≠ 通过）"
else
    echo "测试路径：/media/$REL"
    curl -sI "https://你的域名/media/$REL" | grep -i "^content-type"
fi
```

- **正常**：`content-type: text/html` —— 说明请求落到了前端首页，**文件没被吐出来**
- **危险**：`content-type: image/jpeg`（或 `image/png` 等）——
  说明有人在 Nginx 里开了 `/media/` 的公开别名，
  **任何人猜到路径就能免登录下载学生答题卡**，
  请立刻把那段配置**删掉（或注释掉）**再重载 Nginx
- **跳过**：`media 里还没有图片` —— 不算通过，上传一张配图后必须补验

> ⚠ 注意判据：因为前端是单页应用、最后有 `try_files ... /index.html` 兜底，
> 所以这里**返回 200 是正常的**，要看的是 `content-type` 是不是图片。
> 单纯判断「必须 404」会得到假警报。

**断言四（正向）：关掉了 media，别顺手把 static 也弄坏**

这次的改动动的是 Nginx，所以要反过来证明「该开的还开着」：

```bash
curl -sI https://你的域名/static/admin/css/base.css | head -1
```

- 正常：`HTTP/2 200`
- 异常：404 / 403 → 管理后台会没有样式（页面变成纯文字），
  去查 Nginx 的 `/static/` 是不是还指向 `/opt/zhifou/staticfiles/`，
  以及 `collectstatic` 跑过没有（见第 5 节）

**断言五：用 http（不是 https）直连后端必须拿到 200**

这条验的是 `settings/serverprod.py` 里的 `SECURE_REDIRECT_EXEMPT` 有没有真的生效：

```bash
curl -sI http://127.0.0.1:8000/health/ | head -1
```

- 正常：`HTTP/1.1 200 OK`
- 异常：`HTTP/1.1 301 Moved Permanently` → `serverprod.py` 没生效，
  后端把 http 探活跳走了。后果是 compose 的健康检查判定 unhealthy，
  后面依赖它的服务全部起不来（表现为全站 502 但看不出哪错了）。
  去查 `/opt/zhifou/server/zhifou/settings/serverprod.py` 在不在。

> ★ 别用 `docker compose ps` 看到 healthy 就跳过这条：
> 健康检查用的是容器内 curl，和这里从宿主机直连**不是同一条路径**，
> 两条都过才算真的没问题。

**断言六：从公网用 http 访问普通页面，必须被跳到 https**

这条验的是 Nginx 有没有把 `X-Forwarded-Proto` 透传进来：

```bash
curl -sI http://你的域名/ | grep -i "^location"
```

- 正常：`location: https://你的域名/`（301 跳转到 https）
- 异常：返回 200 而不是跳转 → Nginx 没带 `X-Forwarded-Proto`，
  后端会误判「这是 https 请求」而把浏览器推进 **301 死循环**，
  表现为「网页无法显示，提示重定向次数过多」

> 上面前两项在 `docker-compose.yml` 里已经写死兜底了，
> 只有当你改过 `.env` 或改过 compose 之后才需要重新验一遍。
> 后四项取决于服务器上的 Nginx 配置，换机器 / 改过 Nginx 之后请重验。

### 7.2 写给维护者：本项目**不要**按 Django 默认约定猜表名/列名

绝大多数表都起了**短名**，不是 `<app>_<model>`。写 SQL、写备份脚本、
写数据核对脚本之前，**先看清真实表名**再动手：

```bash
docker compose exec db psql -U zhifou -d zhifou -c '\dt'
```

**⚠ 下面是常见示例，不是全集。** 全仓显式声明 `db_table` 的短名共 **49 张**
（口径：`grep -rh "db_table = " apps/`），加上 Django 自带表与 m2m 表，
目标库实际约 **60+ 张**。完整清单以你这台库上 `\dt` 的输出为准。

已确认的短名（节选）：`asset`、`org`、`user`、`course`、`chapter`、
`knowledge_node`、`knowledge_entry`、`paper`、`paper_item`、`question`、
`assignment`、`assignment_student`、`ingest_batch`、`ingest_item`、
`scan_batch`、`scan_card`、`response`、`score_result`、`pii_mapping`。

**★ 反方向也有坑：不是所有表都短名。**

| 表名 | 归属 | 说明 |
|---|---|---|
| `django_content_type` / `django_session` / `django_migrations` / `django_admin_log` | Django 自带 | 默认名，别去"修正"它 |
| `auth_group` / `auth_permission` / `auth_group_permissions` | Django 自带 | 默认名 |
| `user_groups` / `user_user_permissions` | **本项目自有** | ★ 看着像 Django 默认名，**其实不是** |

最后一行最坑：`accounts.User` 继承了 `PermissionsMixin`，而 User 的
`db_table = "user"`，所以 Django 把它的 m2m 表命名为 `user_groups` /
`user_user_permissions`（规则是 `<db_table>_<字段名>`）——**不是**
`auth_user_groups`。批量授权脚本、备份恢复脚本若按 Django 默认名去找，
会漏掉这两张表，症状是「用户能登录但没有任何权限」。

**★ 还有一类表：`_bak_*`（手工 rename 留下的壳，不是脚本行为）**

`_bak_paper_sheet_binding` / `_bak_scan_batch` / `_bak_scan_card` /
`_bak_sheet_style` / `_bak_sheet_template` 这 5 张表属于**历史遗留数据**，
**不属于本项目 schema**。它们只存在于 PostgreSQL 开发库
（SQLite 开发库里没有），而用 `migrate` 新建的**生产库本来就没有这些表**。

处理方式很简单：**未来的迁移 / 核对脚本显式排除 `_bak_*` 即可**。
不必追责来源，也**不需要清理线上库**（线上是新库，本来就没有）。
（已全量 grep 过 `scripts/` 与 `deploy/server/scripts/`，**没有**任何脚本会创建它们，
所以这不是"正在发生的副作用"，不用去改备份脚本。）

**★ 它唯一会造成后果的路径：拿开发库当 `pg_dump` 源直接灌到生产。**
那样这 5 张表会被一起搬过去，表现为「多出没人认领的表，还能查到几十条旧答题卡模板」。
PG 16 支持通配符，兜底就是加一个参数：

```bash
pg_dump --exclude-table='_bak_*' -U zhifou zhifou > backup.dump
```

- `dumpdata` / `loaddata` 这条路径**天然不受影响**（Django 只导出模型）
- **反向提醒：生产库不会有它们** —— 任何脚本都不许假设它们存在；
  做「表数量对不对」这类校验时，只数 schema 内的表

**列名同样不能靠直觉。** 例如 `asset` 表：

| 想查的东西 | 正确列名 | 容易写错成 |
|---|---|---|
| 文件字节数 | `byte_size` | ~~`size`~~（报 `column "size" does not exist`）|
| 对象存储 key | `oss_key` | — |
| 资源类型 | `kind` | — |
| MIME | `mime` | — |

> ★★ 判据（这一条比上面所有清单都重要）：
> 表名**既可能是与 app 名无关的短名，也可能是 Django 默认名**；
> 列名同样不按直觉（如 `byte_size`）。
> **唯一可靠的来源是目标库上的 `\dt` / `\d <表名>`——记忆和直觉两条路都不可信。**
>
> 遇到 `relation "... " does not exist` 或 `column "... " does not exist`，
> 第一反应永远是「**名字猜错了**」，而不是「数据丢了 / 迁移没跑」。

## 8. 日常运维命令

> 所有命令都要先 `cd /opt/zhifou`。

| 想干什么 | 命令 |
|---|---|
| 看服务状态 | `docker compose ps` |
| 看后端实时日志 | `docker compose logs -f web` |
| 看扫码/worker 日志 | `docker compose logs -f worker_io` |
| 只重启后端 | `docker compose restart web` |
| 改了代码后重新上线 | `docker compose up -d --build` |
| 停掉全部服务 | `docker compose down` |
| 备份数据库 | `docker compose exec db pg_dump -U zhifou zhifou > /opt/zhifou/backups/zf_$(date +%F).sql` |

> `docker compose down` **不会**删掉数据（数据都在数据卷里）。
> 只有加了 `-v` 参数才会删，日常千万别加。

## 9. 常见问题（按踩坑概率排序）

### 坑 1：访问网站显示 502 Bad Gateway

Nginx 通了，但后端没起来。按这个顺序查：

```bash
# 第 1 步：在服务器上（不是容器里）测试后端能不能通
curl -fsS http://127.0.0.1:8000/health/
#   → 返回 {"status": "ok"} = 后端是好的，问题在 Nginx 配置，找第 6 节
#   → 连接被拒绝 / 无响应       = 后端没起来，继续第 2 步

# 第 2 步：看后端状态与报错
docker compose ps          # 看 web 是不是 Up (healthy)
docker compose logs web | tail -50
```

最常见的原因是 `.env` 没填好，日志里会明确写：

- `RuntimeError: 生产环境必须设置 ZF_ALLOWED_HOSTS` → 回去填 `ZF_ALLOWED_HOSTS`
- `KeyError: 'ZF_SECRET_KEY'` → 回去填 `ZF_SECRET_KEY`
- `could not translate host name "db"` → 数据库还没就绪，等 30 秒再看
- `connection refused` → `.env` 里 `ZF_DB_HOST` 被改成了 `127.0.0.1`，改回 `db`

### 坑 2：容器一直 unhealthy，healthcheck 不过

先手动试一次：

```bash
docker compose exec web curl -fsS http://127.0.0.1:8000/health/
```

- 返回 **301**（`Moved Permanently`）→ `serverprod.py` 没放对位置。
  确认 `/opt/zhifou/server/zhifou/settings/serverprod.py` 存在。
  （`SECURE_REDIRECT_EXEMPT` 就是专门解决这个 301 的）
- 返回 **curl: command not found** → 镜像没构建完整，重新 `docker compose up -d --build`

### 坑 3：构建时 `apt-get update` 或 `pip` 卡住不动

网络问题。按顺序试：

1. 配 Docker 镜像加速（见第 1 步）
2. 打开 Dockerfile 里那行被注释掉的 `sed ... mirrors.cloud.tencent.com`
3. 给 pip 也加国内源：在 Dockerfile 的 pip 安装行后面加
   `-i https://mirrors.cloud.tencent.com/pypi/simple/`

### 坑 4：4G 内存不够，容器被系统杀掉

症状：服务跑着跑着突然没了，`docker compose ps` 显示 Exited。

```bash
# 加 2G 的交换空间（临时救急，重启后失效）
fallocate -l 2G /swapfile && chmod 600 /swapfile && mkswap /swapfile && swapon /swapfile
```

各服务的内存上限写在 `docker-compose.yml` 的 `memory:` 里，
加起来约 3.6G。如果服务器长期内存紧张，可以适当调小 worker 的额度。

### 坑 5：`/admin/` 后台页面样式全乱（没有 CSS）

`collectstatic` 没跑，或者 Nginx 的 `/static/` 没指到 `/opt/zhifou/staticfiles`。

```bash
ls /opt/zhifou/staticfiles/admin/css/base.css    # 有这个文件说明 collectstatic 跑过了
docker compose exec web python manage.py collectstatic --noinput
```

### 坑 6：能打开页面，但"AI 出题"报错

正常现象 —— `.env` 里的 `ZF_AI_*` 三项还没填。
题库、组卷、答题卡、批改这些核心功能**不依赖** AI，可以先照常用。

### 坑 7：上传都正常，但重启后图片全没了 / 备份出来的 media 是空目录

先跑第 7.1 节的「断言一」。如果输出是 `/app/.zf-storage` 而不是 `/app/media`，
说明 `ZF_STORAGE_ROOT` 没生效 —— 文件被写进了容器的可写层，
重建容器就丢，而挂在宿主机上的 `/opt/zhifou/media` 一直是空的。

### 坑 8：网页点了"批改/统计"以后要转圈很久

先跑第 7.1 节的「断言二」。如果是 `inline`，说明重算在网页请求里当场算，
`worker_calc` 一直在闲着。把 `.env` 里的 `ZF_TASK_MODE=queued` 补上并
`docker compose up -d` 重新加载即可。

### 坑 9：任务"莫名消失"（扫码提交了却一直没结果，日志也没报错）

Redis 设了 `maxmemory 256mb` + `allkeys-lru`，内存顶满时会淘汰最久未用的 key，
**其中可能包含还没被 worker 消费的 Celery 消息** —— 表现就是任务凭空消失，
而且没有任何报错（见 docker-compose.yml 里 redis 服务的注释）。

查一下队列里是不是积压了：

```bash
docker compose exec redis redis-cli llen p0_critical
docker compose exec redis redis-cli llen p1_generate
docker compose exec redis redis-cli llen p2_recompute
```

- 正常：稳定提交一批作业后，这几个数会先涨后落回 `0`
- 异常：数字一直下不去，或者任务提交后压根没涨 → 看是不是被淘汰了

> ⚠ 别查 `llen celery`：本项目**没有**叫 `celery` 的队列
> （三个队列是 `p0_critical` / `p1_generate` / `p2_recompute`，
> 见 `zhifou/settings/base.py`），查 `celery` 永远返回 0，会得到假通过。

真出现淘汰的话，把 redis 的 `--maxmemory` 调大，或把策略从
`allkeys-lru` 改成 `noeviction`（改完 `docker compose up -d` 生效）。

## 10. 安全提醒

1. **`.env` 里是明文密码**，不要发到微信群、不要提交到 git
2. **`ZF_PII_KEK` 启用后永远不能改**，改了已加密的学生姓名就读不出来了。
   上线前请先把这个值抄一份存到安全的地方
3. 数据库和 Redis **一个端口都没对外暴露**，只有容器之间能互相访问，
   这是有意为之的安全设计，不要为了"方便调试"把它们映射到公网
4. 后端 8000 端口只绑定在 `127.0.0.1`（见 docker-compose.yml 的 `ports`），
   千万不要改成 `8000:8000` —— 那等于绕过 Nginx 把 Django 直接放到公网
5. 服务器防火墙只需要开 **80** 和 **443** 两个端口
6. **不要把 `/opt/zhifou/media` 对外开放**。★ 扫描件里可能有学生姓名和答题卡照片，
   项目的访问控制是「登录 + 本机构校验」，走的是
   `/api/v1/media/assets/{id}/content/` 这个后端接口。
   如果在 Nginx 里加一段 `location /media/ { alias /opt/zhifou/media/; }`，
   等于**绕过登录校验**把学生作业照片放到公网上 —— 不认识的人拿到链接就能下载。
   （`/static/` 是 CSS/JS，不含用户数据，可以直接对外。）
