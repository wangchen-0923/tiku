## 第 0 节 · 五分钟看懂要做什么

**一句话**：在你的服务器上跑起三样东西——**后端程序**（出题、批改、统计）、**数据库**（存题目和学生作答）、**前端网页**（老师和学生看到的页面），再用**宝塔的 Nginx** 把这三样串成一个能用域名访问的网站。

### 数据是怎么流动的（看完这张图就不用再看了）

```
老师 / 学生的浏览器
        │
        │  https://你的域名/login     ← 打开网页
        │  https://你的域名/api/v1/…  ← 页面自动去取数据
        ▼
┌───────────────────────────────────────────────┐
│  宝塔的 Nginx（对外开放 80 / 443 端口）         │
│                                               │
│  /api/…  /admin/…  /health/  ──► 转发给后端容器 │
│  /static/…                   ──► 后台样式文件   │
│  其它所有地址（/login、/assignments/12、/s/xxx）│
│                              ──► 前端网页文件   │
│                                               │
│  ★ 题目配图 / 扫描件不走 Nginx，走                │
│    /api/v1/media/… （要登录 + 校验归属才给看）   │
└───────────────────────────────────────────────┘
        │
        ▼
┌───────────────────────────────────────────────┐
│  后端容器（只监听 127.0.0.1:8000，外网访问不到） │
└───────────────────────────────────────────────┘
        │                    │
        ▼                    ▼
   数据库容器 db        缓存容器 redis
```

### 服务器上这几个目录是干什么的（记不住也没关系，脚本会自动建）

| 目录 | 放什么 | 谁写进去的 |
| --- | --- | --- |
| `/opt/zhifou/` | 部署总目录：`docker-compose.yml`、`.env`、脚本 | 你上传 |
| `/opt/zhifou/staticfiles/` | 后台管理页面的 CSS / JS | `collectstatic` 自动导出 |
| `/opt/zhifou/media/` | 题目配图、扫描件、答题卡 PDF | 老师上传时自动存 |
| `/opt/zhifou/backups/` | 备份文件 | 备份脚本 |
| `/opt/zhifou/scripts/` | 4 个运维脚本 | 你上传 |
| `/opt/zhifou/nginx/` | Nginx 配置（**整个目录**都要传，不能只传一份） | 你上传 |
| `/www/wwwroot/zhifou/dist/` | 前端网页文件（`npm run build` 的产物） | 你上传 |

### 服务器里会跑 6 个小容器（不用管它们，知道就行）

| 容器 | 干什么 | 你要知道的 |
| --- | --- | --- |
| `db` | PostgreSQL 数据库，存题目、学生作答、账号 | 它**不对外开任何端口**，只有别的容器能连 |
| `redis` | 缓存 + 任务队列的"排队处" | 同上，不对外 |
| `web` | 后端主程序（Django），处理所有 `/api/`、后台管理 | 只监听 `127.0.0.1:8000`，**公网访问不到** |
| `worker_io` | 干「扫码识别、导入解析、AI 出题」这类活 | 不出结果时看它的日志 |
| `worker_calc` | 干「学情重算、统计、批改、导出」这类活 | 同上 |
| `beat` | 定时任务的闹钟，负责按时把活派给上面两个 | 全站只能有 1 个，不要多开 |

### 4G 内存是怎么分的（了解就行，别改）

| 容器 | 内存上限 | 说明 |
| --- | --- | --- |
| `web` | 896M | 2 个 worker × 2 线程，4 核机器开多了反而更慢 |
| `worker_io` | 1024M | 要加载 OCR 模型，占得最多 |
| `worker_calc` | 512M | |
| `db` | 640M | |
| `redis` | 320M | 到 256M 就淘汰最久未用的缓存 |
| `beat` | 256M | |
| **合计** | **约 3.6G** | 剩下的留给系统 + 宝塔 + Nginx |

> 这就是为什么第 1 节建议你把宝塔里用不到的 MySQL / PHP 停掉 —— 4G 内存确实紧。
> 如果内存实在不够，可以临时加 2G 交换空间救急（见第 6 节故障 14）。

## 第 1 节 · 准备工作清单

逐条打勾，全部齐了再往下走。

### 1.00 服务器还没装 Docker 怎么办（先做这一节，再做 1.0）

**先判断你要不要看这一节。** 在宝塔终端里敲：

```bash
docker compose version
```

- 能打印出 `Docker Compose version v2.x.x`（或 v5.x.x）→ Docker 已经装好了，**跳过本节，直接看 1.0 节**。
- 显示 `bash: docker: command not found` → 服务器上压根没装 Docker，**照着本节一步步做**。

> **这一节在说什么（大白话）**：Docker 是让知否跑起来的"底座"，它把 Python、数据库、
> 缓存这些东西都装进一个个"盒子"里，跟服务器本身的系统隔开。没这个底座，后面全部免谈。
> 装它一共 7 条命令，全部复制粘贴即可，中间不需要你做任何判断。

在宝塔终端里**依次**执行下面 7 步（一行一行来，每步看到提示再走下一步）：

```bash
# 1. 装仓库管理工具（如果已经装过会提示"无变化"，属正常）
dnf install -y dnf-plugins-core

# 2. 添加腾讯云的 Docker 软件源（比官方源快，且在国内能访问）
dnf config-manager --add-repo=https://mirrors.cloud.tencent.com/docker-ce/linux/centos/docker-ce.repo

# 3. ★ 关键一步：把源里的下载地址换成腾讯云镜像
#    （不加这步会去连 download.docker.com，腾讯云机器上常常下不动或找不到 centos/9 路径）
sed -i 's|download.docker.com|mirrors.cloud.tencent.com/docker-ce|g' /etc/yum.repos.d/docker-ce.repo

# 4. 如果上一步之后仍报找不到 centos/<版本号> 的路径，再把版本号写死成 9
#    （OpenCloudOS 9 的 $releasever 有时解析不出来）
sed -i 's|\$releasever|9|g' /etc/yum.repos.d/docker-ce.repo

# 5. 安装 Docker 本体 + 我们要用的 compose 插件
dnf install -y docker-ce docker-ce-cli containerd.io docker-buildx-plugin docker-compose-plugin --nobest

# 6. 设为开机自启并立刻启动
systemctl enable --now docker

# 7. 验证（注意 compose 前面是空格）
docker compose version
docker info | head -n 5
```

**每一步应该看到什么：**

| 步 | 正常是什么样 | 什么样算有问题 |
| --- | --- | --- |
| 1 | 滚一堆英文，最后出现 `Complete!`；如果已经装过会显示 `Nothing to do` —— **都算正常** | 出现 `No match for argument` 且长时间不动 |
| 2 | 出现 `Adding repo from: https://mirrors.cloud.tencent.com/...` | 提示连不上（检查服务器能不能上网） |
| 3、4 | **没有任何输出就是对的**（`sed` 改文件不回显） | 提示 `No such file or directory` → 说明第 2 步没成功，回去重做 |
| 5 | 滚很多行，**这一步要几分钟**，最后出现 `Complete!` | 出现 `Error: Unable to find a match` → 回到第 3、4 步重做 |
| 6 | 出现 `Created symlink ...`（开机自启建立成功），然后光标直接回来 | 卡住不动 |
| 7 | 打印出 `Docker Compose version v2.x.x` 或更高，接着打印 5 行 Docker 信息 | `command not found` → 看下面 |

**三个必须知道的点：**

1. **第 5 步里的 `docker-compose-plugin` 不能省。** 它才是带空格的 `docker compose`。
   老教程里那种带横杠的 `docker-compose` v1 我们这套配置跑不了（它不认 `name:` 和 `depends_on`）。
2. **第 3 步那条 `sed` 不是可选的。** 腾讯云那个源配置文件里面写的下载地址仍然是官方域名
   `download.docker.com`，不改成镜像地址就会下载失败 —— 这是腾讯云机器上的已知坑。
3. **如果你之前在宝塔「软件商店 → Docker管理器」里装过 Docker**，那里很可能**只带了老版
   docker-compose**，仍然要回到命令行执行第 5 步装插件，并用第 7 步确认版本。

**判据（只有一条）**：第 7 步只要能打印出 `Docker Compose version v2.x` 或更高（**v5 也算**），
就可以回到 1.0 节继续；如果还是 `command not found`，**把终端输出整段发回来，不要自己瞎试。**

### 1.0 先确认 Docker 版本（★ 这一步不做，后面一定会失败）

在宝塔终端里执行：

```bash
docker compose version
```

**必须是 `v2` 或更高**（`v2.x.x`、`v5.x.x` 都可以 ✅；**只有 `v1.x.x` 不行** ❌）。

> 看到 `Docker Compose version v5.1.1` 这种**完全没问题**，不要用老教程去降级它 ——
> v5 向后兼容，知否需要的 `name:` 和 `depends_on condition` 它都支持。
> **判据只有一条：不是 1.x 就行。**

> ⚠ **注意命令写法**：是 `docker compose`（**中间一个空格**），不是 `docker-compose`（横杠）。
> 如果你敲的是带横杠的 `docker-compose`，那是老版本 v1，**知否会启动失败**，
> 而且报错会很难懂（它不认配置文件里的 `name:` 和 `depends_on condition`）。
> 带横杠的 v1 连 `compose` 这个子命令都没有，所以敲 `docker compose version`
> 会直接提示 command not found —— 这本身就是一条可靠的判断依据。
>
> 如果提示 **`bash: docker: command not found`**（连 Docker 本身都没有）
> → **先回到上一节 1.00 装 Docker**，装完再来这里。
>
> 如果 Docker 有、只是 compose 不对（提示 `docker compose: command not found`，
> 或输出是带横杠的 `docker-compose version 1.x.x`）：
> ```bash
> dnf install -y docker-compose-plugin      # OpenCloudOS / CentOS
> # Ubuntu / Debian 用： apt-get install -y docker-compose-plugin
> ```
> 装完再执行一次 `docker compose version`，确认输出的是 **v2 或更高**（不是 1.x）。
>
> 顺带确认 Docker 本身在跑：`systemctl status docker` 看到 `active (running)` 就行。
> 没装 Docker 的话：宝塔 → 软件商店 → 搜索「Docker管理器」→ 安装。

### 1.1 服务器

- [ ] 系统 OpenCloudOS 9，4 核 4G，能连外网
- [ ] 宝塔面板 11.4 能正常打开
- [ ] **4G 内存很紧张**。知否本身要跑：PostgreSQL + Redis + 后端 + 2 个后台任务进程。
      如果宝塔里还装着**你用不到**的 MySQL、PHP，建议先停掉（**确认真的没在用再停**）：

      ```bash
      # 这两行只是建议，自己确认过再敲，脚本不会替你执行
      systemctl stop mysqld  && systemctl disable mysqld
      systemctl stop php-fpm && systemctl disable php-fpm
      ```

      判断方法：宝塔 → 软件商店 → 已安装，看看有没有 MySQL / PHP；
      宝塔 → 网站，看看有没有别的网站在用它们。**没有就可以停。**

### 1.2 域名

- [ ] 域名**已备案**（腾讯云买的域名在腾讯云备案）
- [ ] 域名**已解析到这台服务器**：在域名解析里加一条 A 记录，主机记录填 `tiku`（或 `@`），记录值填服务器的**公网 IP**
- [ ] **服务器防火墙放行了 80 和 443 端口**（两处都要开，缺一处等于没开）：
      - 腾讯云控制台 → 服务器 → **安全组**（轻量应用服务器里叫「**防火墙**」）→ 放行 `TCP:80`、`TCP:443`
      - 宝塔面板 → **安全** → **系统防火墙** → 放行 `80`、`443`
      > CVM 的**默认安全组通常只放行 22**（Windows 再加 3389），80/443 要自己加；
      > 轻量应用服务器一般默认就开着，但也要看一眼确认。
- [ ] **放行到底生效了没有？必须从"服务器外面"测**：
      **拿手机关掉 WiFi、改用 4G 流量，打开 `http://你的域名/`**。
      能看到页面（哪怕只是宝塔的「站点创建成功」）就说明 80 通了。
      > 为什么不能在服务器上测：走 `127.0.0.1` 的请求根本不经过安全组，
      > **安全组全封的情况下，本机 `curl 127.0.0.1` 照样返回 200**，会把你骗过去，
      > 让你以为已经好了，然后卡在 2.6 申请证书那一步。
      >
      > ⚠ 80 不通**不只是"用户打不开网站"这么简单**：Let's Encrypt 的验证服务器是
      > 从**公网外面**来访问 `http://你的域名/.well-known/...` 的，80 进不来，
      > 2.6 申请证书就**必然失败**，而且失败提示不会告诉你真实原因。
- [ ] 解析是否生效？在你自己电脑上打开命令行执行 `ping tiku.xxx.com`，看到的 IP 应该是服务器 IP。
      （还没生效就等 10 分钟再试，解析生效前申请证书会失败）

### 1.3 怎么进宝塔终端（后面所有命令都在这里敲）

路径：**宝塔面板左侧菜单 → 终端**（第一次打开会让你输一次服务器 root 密码，勾上「记住密码」）。
进去之后看到类似 `[root@xxx ~]#` 就说明可以敲命令了。

> 粘贴命令：在终端里点**右键 → 粘贴**，或者按 `Shift + Insert`。**不要用 Ctrl+V**。

### 1.4 需要提前准备的东西

- [ ] 一份前端网页产物：在本地 `web/` 目录执行 `npm run build`，得到 `web/dist` 文件夹（这一步通常由技术人员做，你只要拿到这个文件夹打到 zip 里）
- [ ] 后端部署文件（技术人员提供）：`docker-compose.yml`、`.env.prod.example`、`Dockerfile`
- [ ] 本目录下的 4 个脚本（`first_deploy.sh`、`update.sh`、`backup.sh`、`restore.sh`）+ **3 个 nginx 文件**（`zhifou.conf`、`zhifou.http-only.conf`、`proxy_headers.conf`）

> ★ 三个 nginx 文件**一个都不能少**，尤其 `proxy_headers.conf`。
> 它不传，后面 2.7 换成完整版配置、点保存时会直接报错：
> `[emerg] open() "/opt/zhifou/nginx/proxy_headers.conf" failed`
> 因为完整版里 `/api/`、`/admin/`、`/health/` 三段都 `include` 了这个文件。
> 所以 `nginx/` 目录要**整个目录一起传**，不要只挑 `zhifou.conf` 发过去。

## 第 2 节 · 宝塔面板点点点的操作

这一节**完全用鼠标**，不敲命令。**按顺序做完，顺序不能反。**

> ### ⏱ 关于 HTTPS 证书，时序是这样的（最容易搞反的一步）
>
> ```
>   ① 建站点  →  ② 粘贴【临时版】配置（只有 80 端口）
>                        ↓
>              ③ 申请 Let's Encrypt 证书（只有这时才申请得下来）
>                        ↓
>              ④ 换成【正式版】配置（80 跳 443 + 443 全站）
> ```
>
> **为什么不能一上来就粘正式版**：正式版里有 443 段，但证书文件此刻还不存在，
> Nginx 会直接起不来 → 站点起不来 → 又申请不了证书 → 卡死循环。
> 所以必须先用只有 80 端口的临时版把证书申请下来，再换正式版。
>
> 配置文件里的 `zhifou.http-only.conf` = 临时版，`zhifou.conf` = 正式版，别粘错。

### 2.1 建一个站点

1. 宝塔面板 → **网站** → 顶部先点 **PHP项目** 分页签 → 再点右上角 **添加站点**
   > 新版宝塔（含 11.4）的「网站」页面顶部有 `PHP项目 / Java项目 / Node项目 / 其它项目`
   > 四个分页，默认不一定是「PHP项目」。**进去看不到「添加站点」按钮，就先点一下顶部的 PHP项目**，
   > 按钮就出来了。腾讯云专享版和标准版这一步完全一样，没有区别。
2. 域名：填 `你的域名`（例如 `tiku.xxx.com`）。一行一个，可以填多个
3. 根目录：填 `/www/wwwroot/zhifou/dist`
4. 数据库：**选「不创建」**（数据库我们放在 Docker 容器里）
5. FTP：**选「不创建」**
6. PHP 版本：**选「纯静态」**
7. 点 **提交**

> 建完之后，宝塔会自动创建 `/www/wwwroot/zhifou/dist` 这个目录。

#### 建站后必须立刻做：确认首页没被宝塔默认页盖掉

宝塔建站时会往「根目录」写一个「恭喜，站点创建成功」的 `index.html`
（顺带还会生成 `404.html` 和 `.user.ini`）。
如果顺序搞反了（**先传前端、后建站**），它会把你的 `index.html` **直接盖掉**，
而且**不弹任何提示** —— 表现就是打开网站只看到「站点创建成功」几个字。

本节 2.1（建站）→ 2.3（传前端）的顺序本身就是对的：建站时目录还是空的，随便它写，
2.3 传上去正好把默认页盖掉。**但如果你之前已经先传过前端文件，建站前先备份一次**：

```bash
# ① 建站前：备份现有前端（提示"没有那个文件"就是还没传，没关系，跳过即可）
BK=/root/zf-dist-bak-$(date +%Y%m%d-%H%M%S)
cp -a /www/wwwroot/zhifou/dist "$BK" && echo "已备份到 $BK"
```

建站做完、2.3 上传做完，各执行一次下面这条：

```bash
# ② 判断首页是不是被盖了
grep -q "站点创建成功" /www/wwwroot/zhifou/dist/index.html \
  && echo "❌ 被宝塔默认页盖了，按 ③ 还原" \
  || echo "✅ 正常，是自己的首页"
```

**应该看到**：`✅ 正常，是自己的首页`。看到 `❌` 就执行 ③ 还原：

最后复核尺寸和资源目录对不对（字节数要和本地 `web/dist/index.html` 一致）：

```bash
ls /www/wwwroot/zhifou/dist/assets | head -n 5
```

如果 `assets` 是空的或者报「没有那个目录」，说明 zip 解压多了一层，回 2.3 第 4 步处理。

### 2.6 申请 SSL 证书（HTTPS）

#### 点「申请」之前，先花 1 分钟把「验证通道」试通

Let's Encrypt 的「文件验证」是这样工作的：它从**公网外面**去访问
`http://你的域名/.well-known/acme-challenge/一串随机字符`，
能读到那个临时文件，才承认这个域名是你的。
所以能不能申请成功，跟「网站做得漂不漂亮」没关系，只跟**这条通道通不通**有关。
先自己试一遍，通了再点申请；不通就点，只会换来一句看不懂的英文报错，
然后你完全不知道是域名、端口、还是配置的问题。

**① 看 Nginx 有没有在听 80 端口**

```bash
ss -lntp | grep -E ":80 |:443 "
```

**应该看到**：有一行 `LISTEN`，进程名是 `nginx`，地址是 `:80`。
（现在还只有临时配置，`:443` 查不到是正常的，不用管。）
一行都没有 → 回 2.2 确认临时版配置真的保存成功了，然后在终端执行 `bt reload` 再看一次。

**② 造一个测试文件，从本机访问**

把下面命令里的 `你的域名` 换成真实域名（例如 `lszyzz.zj.cn`），整段粘贴执行：

```bash
mkdir -p /www/wwwroot/zhifou/dist/.well-known/acme-challenge
echo ok > /www/wwwroot/zhifou/dist/.well-known/acme-challenge/t.txt
curl -s -o /dev/null -w "本机=%{http_code}\n" \
  -H "Host: 你的域名" http://127.0.0.1/.well-known/acme-challenge/t.txt
```

**应该看到**：`本机=200`。
看到 `404` → `.well-known` 目录没建对，或 2.2 的临时配置没生效（临时配置里专门有一段
`location ^~ /.well-known/acme-challenge/`，它要是被删了就会 404）；
看到 `000` → Nginx 压根没起来。

**③ 从外网访问同一个文件（这一步才是决定性证据）**

```bash
curl -s -o /dev/null -w "外网=%{http_code}\n" http://你的域名/.well-known/acme-challenge/t.txt
```

**应该看到**：`外网=200`。**②③ 两条都 200，才叫通道真的通了**，这时再去点申请。
只出现「本机=200、外网不通」= **安全组 / 防火墙没放行**，回第 1.2 节把 80 开出来。
（再强调一次：本机 200 不能当「通过」用，它会骗人。）

**④ 测完把测试文件删掉**（不删会一直留在网站根目录里）

```bash
rm -f /www/wwwroot/zhifou/dist/.well-known/acme-challenge/t.txt
```

通道试通了，现在才轮到点「申请」：

1. 宝塔 → **网站** → **站点** → **设置** → **SSL**
2. 选 **Let's Encrypt** → 验证方式选 **文件验证**
3. 点 **申请**
4. 成功的话会显示证书内容和到期时间
5. **不要打开「强制 HTTPS」开关**（我们的配置文件里已经做了跳转，开了会重复）
6. 记下页面上显示的 **证书路径** 和 **密钥路径**（下一步要用）

> 如果申请失败，先回头看你 ③ 的结果，别瞎猜：
> - **③ 外网不是 200** → 通道问题（安全组 / 防火墙 / 解析没生效），先把第 1.2 节做完再来；
> - **③ 外网是 200 但申请还是失败** → 多半是短时间反复点触发了 Let's Encrypt 的频率限制，
>   等 1 小时再试一次，不要连续点。

### 2.7 换成正式版 Nginx 配置

> **这一步有一个"跳过它、三个月后必出事故"的动作，先看清楚再动手。**
>
> 宝塔把证书那两行 `ssl_certificate` 写在站点配置里，并且靠 `#SSL-START … #SSL-END`
> 这段注释来判断「这个站点归它管」。我们整段替换配置，这段注释就没了。
> 后果分两层，要分清：
>
> - **证书文件本身还能续期**（续期只是把新文件写到同一个路径，跟配置怎么写无关）；
> - **但宝塔的「SSL」页面会跟我们的配置打架**：你以后在面板上点「强制 HTTPS」、
>   或者重新部署一次证书时，宝塔找不到 `#SSL-START` 就会**再插一套** `ssl_certificate`，
>   同一个 server 块里出现两条重复指令 → `nginx -t` 直接失败 → 整个站点打不开。
>
> 这就是典型的「今天好好的，三个月后突然挂掉，还查不出原因」。
> 处理方法就一句话：**证书那两行永远归宝塔所有，我们只管其它配置。**

**第 1 步：先把宝塔生成的证书段抄出来（必须在替换之前做）**

1. 宝塔 → **网站** → **站点** → **设置** → **配置文件**
2. 在框里找到 `#SSL-START` 开头、`#SSL-END` 结尾的那一整段，**连注释一起选中复制**，
   粘到记事本里存着
3. 不确定有没有这段，用命令看（下面 `你的域名` 记得换成真实域名）：

   ```bash
   grep -n "SSL-START\|SSL-END" /www/server/panel/vhost/nginx/你的域名.conf
   ```

   **应该看到**：`SSL-START` 和 `SSL-END` 各出现一次，前面带行号。
   什么都没输出 = 这段不存在，说明 2.6 的证书还没真正部署到站点上，回 2.6 重做一次。

**第 2 步：替换成正式版配置**

1. 还是「配置文件」这个框，全选删除
2. 粘贴 `nginx/zhifou.conf` 的**全部内容**
3. 把两处 `server_name  zhifou.example.com;` 改成你的域名（**有 2 处**，80 段和 443 段各一个）
4. 把 `ssl_certificate` 两行里的 `<你的域名>` 换成真实域名。**拿不准就先列目录看真实名字**：

   ```bash
   ls -l /www/server/panel/vhost/cert/
   ```

   **应该看到**：一个以你的**域名**命名的目录（例如 `lszyzz.zj.cn`），进去有
   `fullchain.pem`、`privkey.pem` 两个文件。
   **以 ls 显示的名字为准**。写成 `zhifou` 是错的 —— 宝塔按「站点名（= 建站时填的
   第一个域名）」建证书目录，跟根目录叫什么都不相干。
   填错的后果是"Nginx 起不来"，而报错是英文的，现场基本看不出原因。

**第 3 步：把第 1 步抄下来的证书段贴回去，并删掉我们自带的两行**

1. 把记事本里那段 `#SSL-START … #SSL-END` **原样粘贴**到 443 段里
2. **删掉我们文件自带的那两行** `ssl_certificate` / `ssl_certificate_key`
   （在 `── HTTPS 证书 ──` 注释块的最末尾，带 `<你的域名>` 占位符的那两行）
3. 点 **保存**。宝塔保存时会自动检查语法，报红字就对照第 6 节的故障表

**第 4 步：验证"证书只有一份"（这条最关键，出来 2 就必须停下）**

```bash
grep -c "ssl_certificate " /www/server/panel/vhost/nginx/你的域名.conf
nginx -t
```

**应该看到**：第一条输出 `1`，第二条输出 `syntax is ok` + `test is successful`。
第一条输出 `2` = 重复了（我们自带的两行没删干净，或者证书段贴了两遍），
**立刻回去删到只剩 1 份**；带着重复指令 Nginx 起不来，整站会打不开。

> 想确认 Nginx 真的在用最新那份证书文件，跑下面两条，**输出必须一字不差**：
>
> ```bash
> openssl x509 -in /www/server/panel/vhost/cert/你的域名/fullchain.pem -noout -enddate
> echo | openssl s_client -connect 127.0.0.1:443 -servername 你的域名 2>/dev/null | openssl x509 -noout -enddate
> ```
>
> 两条不一致 = Nginx 还在用某个旧证书，说明路径指错了。

### 步骤 1：生成密钥并填写 `.env`

在宝塔终端里执行：

```bash
cd /opt/zhifou
ls
```

**应该看到**：`docker-compose.yml`、`.env.prod.example`、`scripts`、`nginx` 等。

**★ 推荐做法：一条命令生成并写好 `.env`（不用手工编辑文件）**

把下面整段复制进终端，**只需要改第一行的域名**：

```bash
DOMAIN="tiku.xxx.com"      # ← 只改这一行，换成你的域名，不带 https://、不带斜杠
cd /opt/zhifou || exit 1
rnd(){ head -c 200 /dev/urandom | base64 -w0 | tr -dc 'A-Za-z0-9' | cut -c1-"$1"; }
ZK="$(rnd 56)"; DBP="$(rnd 32)"; KEK="$(head -c 32 /dev/urandom | base64 | tr -d '\n')"
cat > .env <<EOF
# 知否 · 生产环境变量（脚本生成，勿提交 git，勿外传）
DJANGO_SETTINGS_MODULE=zhifou.settings.serverprod
ZF_SECRET_KEY=$ZK
ZF_ALLOWED_HOSTS=$DOMAIN
ZF_CORS_ORIGINS=
ZF_CSRF_TRUSTED_ORIGINS=
POSTGRES_DB=zhifou
POSTGRES_USER=zhifou
POSTGRES_PASSWORD=$DBP
ZF_DB_NAME=zhifou
ZF_DB_USER=zhifou
ZF_DB_PASSWORD=$DBP
ZF_DB_HOST=db
ZF_DB_PORT=5432
ZF_REDIS_URL=redis://redis:6379/0
ZF_CACHE=
ZF_SCAN_RECOGNITION=celery
ZF_TASK_MODE=queued
ZF_STORAGE_BACKEND=local
ZF_STORAGE_BUCKET=
ZF_STORAGE_ENDPOINT=
ZF_STORAGE_ROOT=/app/media
ZF_MEDIA_ROOT=/app/media
ZF_PII_KEK=$KEK
ZF_AI_BASE_URL=
ZF_AI_API_KEY=
ZF_AI_MODEL=
ZF_OSS_BUCKET=
ZF_OSS_ENDPOINT=
ZF_OSS_REGION=
ZF_OSS_KEY=
ZF_OSS_SECRET=
TZ=Asia/Shanghai
EOF
chmod 600 .env
echo "──────────────── 自检 ────────────────"
ls -l .env
[ "$(grep '^POSTGRES_PASSWORD=' .env | cut -d= -f2-)" = "$(grep '^ZF_DB_PASSWORD=' .env | cut -d= -f2-)" ] \
  && echo "OK  两处数据库密码一致" || echo "BAD 两处数据库密码不一致"
grep -qE '<|CHANGE_ME|YOUR_' .env && echo "BAD 还有未填写的占位符" || echo "OK  没有残留占位符"
grep -qE '^[A-Z_]+[[:space:]]+=' .env && echo "BAD 等号左边有空格" || echo "OK  等号两边无空格"
echo "OK  允许访问的域名：$(grep '^ZF_ALLOWED_HOSTS=' .env | cut -d= -f2-)"
docker compose config --quiet && echo "OK  docker compose 能正确解析配置"
```

**全部打印 `OK` 就说明写好了**，可以跳到步骤 2。

> ★ 这条命令做的事：生成 3 个随机密钥（`ZF_SECRET_KEY`、`POSTGRES_PASSWORD`=`ZF_DB_PASSWORD`、`ZF_PII_KEK`），
> 并按正确的值写好 `ZF_STORAGE_ROOT` / `ZF_TASK_MODE` / `ZF_SCAN_RECOGNITION` 这几项容易写错又**不报错**的开关。
> 生成的口令只含大小写字母和数字，所以不会出现空格、`#`、引号把配置搞坏的情况。
>
> ★ 写完后请用宝塔「文件」把 `/opt/zhifou/.env` **下载一份到你自己电脑存好**（里面有密钥，丢了就得重来）。

<details>
<summary>不推荐：手工编辑（只在需要逐项调整时看）</summary>

生成三个密钥：

```bash
openssl rand -base64 48    # 填到 ZF_SECRET_KEY
openssl rand -base64 32    # 填到 ZF_PII_KEK
openssl rand -hex 16       # 同时填到 POSTGRES_PASSWORD 和 ZF_DB_PASSWORD（两处必须一模一样）
```

```bash
cp /opt/zhifou/.env.prod.example /opt/zhifou/.env
```

然后：宝塔 → **文件** → `/opt/zhifou` → 双击 `.env` → 填好上面几串 + `ZF_ALLOWED_HOSTS` → **保存**。

</details>

除了上面三串密钥，`.env` 里**这 4 项也必须核对**（模板里已经给了默认值，改错了不会报错、但会静默出问题）：

| 变量 | 必须是什么 | 错了会怎样（不报错，很难发现） |
| --- | --- | --- |
| `ZF_STORAGE_ROOT` | `/app/media` | 上传的扫描件/答题卡会存进容器内部，**重建容器就全丢**，而且备份里的 media 是空包 |
| `ZF_TASK_MODE` | `queued` | 学情重算会在网页进程里同步算，页面变慢，后台的 worker_calc 一条任务都收不到 |
| `ZF_SCAN_RECOGNITION` | `celery` | 扫码识别变成同步执行，全班一起扫会卡住页面 |
| `ZF_DB_HOST` | `db` | 后端会去连 127.0.0.1 的 PostgreSQL，连不上 |

> 这 4 项不用你手工核对——首次部署脚本跑完会自动检查并在终端里告诉你结果。

另外一条**正常的告警**，看到不用紧张：
后端日志里会出现 `生产环境仍在使用本地文件存储` 这条警告。
单机部署**本来就用本地磁盘存文件**，这是预期行为，不是故障。

> ⚠ `.env` 里凡是写着 `<请生成>`、`<改成…>`、`请填写`、`CHANGE_ME` 的地方**必须全部改掉**，否则部署脚本会拒绝执行。

### `.env` 里每一项都是干什么的（完整清单，看一眼心里有数）

| 变量 | 填什么 | 不填/填错会怎样 |
| --- | --- | --- |
| `DJANGO_SETTINGS_MODULE` | `zhifou.settings.serverprod`（**照抄，别改**） | 改了就起不来 |
| `ZF_SECRET_KEY` | `openssl rand -base64 48` 生成的长串 | 后端直接报错退出 |
| `ZF_ALLOWED_HOSTS` | 你的域名，多个用英文逗号隔开，**不带 https://** | 访问显示 400 Bad Request |
| `POSTGRES_DB` / `POSTGRES_USER` | 建议都填 `zhifou` | 建库用的 |
| `POSTGRES_PASSWORD` | `openssl rand -hex 16` 生成的串 | 缺了容器直接拒绝启动 |
| `ZF_DB_NAME` / `ZF_DB_USER` | 必须和上面 `POSTGRES_DB` / `POSTGRES_USER` **完全一样** | 报 `role does not exist` |
| `ZF_DB_PASSWORD` | 必须和 `POSTGRES_PASSWORD` **完全一样** | 后端连不上数据库 |
| `ZF_DB_HOST` / `ZF_DB_PORT` | `db` / `5432`（**照抄，别改成 127.0.0.1**） | 改成 127.0.0.1 会连不上 |
| `ZF_REDIS_URL` | `redis://redis:6379/0`（**照抄**） | 缓存和队列失效 |
| `ZF_PII_KEK` | `openssl rand -base64 32` 生成的串 | ★ **上线后永远不要改**，改了已加密的学生姓名就读不出来了 |
| `ZF_STORAGE_BACKEND` | `local`（单机部署填这个） | 填别的需要另配对象存储 |
| `ZF_STORAGE_ROOT` | `/app/media` | 不填 → 上传的文件重启容器就丢 |
| `ZF_MEDIA_ROOT` | `/app/media` | 同上 |
| `ZF_TASK_MODE` | `queued` | 填 `inline` → 后台任务容器空转、页面变慢 |
| `ZF_SCAN_RECOGNITION` | `celery` | 填别的 → 扫码识别卡住页面 |
| `ZF_CACHE` | 留空（走 Redis） | — |
| `ZF_AI_API_KEY` / `ZF_AI_BASE_URL` / `ZF_AI_MODEL` | 可选，AI 出题才需要 | **不填也能用**：题库、组卷、答题卡、批改都不依赖 AI |
| `ZF_CORS_ORIGINS` / `ZF_CSRF_TRUSTED_ORIGINS` | 留空（同一域名访问不需要） | — |
| `TZ` | `Asia/Shanghai` | 时间显示会差 8 小时 |

> 填的时候三条铁律：等号两边**不加空格**、值**不加引号**、值里**不要有 `#` 和空格**。

### 4.2 反向验收：确认图片不能被免登录下载（★ 安全，必做）

学生的答题卡照片里有姓名，只能走「登录 + 校验归属机构」的接口取，
**绝对不能**让 Nginx 把它当普通静态文件对外开放。验一遍：

```bash
# 挑一张真实存在的【图片】去试（不要拿目录本身或 txt / pdf）
REL=$(cd /opt/zhifou/media && find . -type f \( -iname '*.jpg' -o -iname '*.jpeg' -o -iname '*.png' \) | head -1 | sed 's|^\./||')
echo "测试路径：/media/$REL"
curl -sI "https://你的域名/media/$REL" | grep -i "^content-type"
```

- **正常**：`content-type: text/html` —— 请求落到了前端首页，**文件没被吐出来** ✅
- **危险**：`content-type: image/jpeg`（或 `image/png`、`application/pdf` 等）——
  说明有人在 Nginx 里开了 `/media/` 的公开别名，
  **任何人猜到路径就能免登录下载学生答题卡** ❌ 请立刻把那段配置注释掉。

> ⚠ **判据是 content-type，不是状态码 —— 不能用 404 判断。**
> 因为前端是单页应用，最后有 `try_files ... /index.html` 兜底，
> 任何不存在的路径都会返回 **200 + text/html**。
> 所以「返回 200」在这里是**正常的**；只有 `content-type` 变成图片/文件类型才是危险信号。
> 如果按「必须 404」判，一定误报，然后你会去瞎改一份本来没问题的配置。

> ⚠ **取样只挑图片**（jpg / jpeg / png）。拿 txt、pdf 或目录本身去试，
> `content-type` 五花八门，容易误判。

> ⚠ **「跳过」不等于「通过」。**
> 如果 `/opt/zhifou/media` 里还没有任何图片（新环境），这条**现在验不了** ——
> **等老师上传过第一张配图之后，一定要回来补验一次。**

正确、设计上认可的读取方式是登录后的接口：
`/api/v1/media/assets/{id}/content/`，不是任何静态路径。

### 5.6 备份

**手工备份一次：**

```bash
bash /opt/zhifou/scripts/backup.sh
```

产物在 `/opt/zhifou/backups/`，文件名带日期，例如：

```

media-20261020-030000.tar.gz  ← 题目配图 / 扫描件
static-20261020-030000.tar.gz ← 后台样式
MANIFEST-20261020-030000.txt  ← 说明文件，写了这三个是一组
```

```bash

```

或者用宝塔的图形界面：宝塔 → **计划任务** → 任务类型「shell脚本」 → 执行周期「每天 03:00」→

> ⚠ **备份文件留在服务器上，硬盘坏了照样全没。**
> 请定期：宝塔 → 文件 → `/opt/zhifou/backups` → 勾选 `.dump` 文件 → **下载**，存到自己电脑上。

> ⚠ 如果备份脚本**报错退出**并提示 media 目录是空的，那不是「没文件」这么简单 ——


## 第 6 节 · 常见故障对照表

按「现象」找，按顺序试「一句话解决办法」。

| # | 现象 | 原因 | 一句话解决办法 |
| --- | --- | --- | --- |
| 1 | `/admin/` 打开是**纯白板，没有样式** | 漏了 collectstatic，或 Nginx 的 `/static/` 没指向对 | 执行 `cd /opt/zhifou && docker compose -p zhifou run --rm web python manage.py collectstatic --noinput`，再确认 Nginx 里 `alias /opt/zhifou/staticfiles/;` 这行在；浏览器 `Ctrl+F5` 强刷 |
| 2 | **502 Bad Gateway** | 后端容器没起来，或 Nginx 转发的端口不对 | 执行 `cd /opt/zhifou && docker compose -p zhifou ps` 看 `web` 是不是 `Up`；不是就看 `docker compose -p zhifou logs web`。再确认 Nginx 里是 `proxy_pass http://zhifou_backend;`（指向 `127.0.0.1:8000`） |
| 3 | 首页能开，但 `/login`、`/assignments/12`、`/s/xxx` **刷新就 404** | Nginx 少了 `try_files` 兜底 | 确认 443 段最后是 `location / { try_files $uri $uri/ /index.html; }`；改完在宝塔点保存（或 `nginx -t && nginx -s reload`） |
| 4 | **登录成功，一刷新/一点就掉线** | ① `.env` 的 `ZF_ALLOWED_HOSTS` 没填或和域名不一致；② Nginx 没传 `X-Forwarded-Proto`，后端以为还是 http 就把你跳走了 | ① `.env` 里 `ZF_ALLOWED_HOSTS=tiku.xxx.com`（不带 https://）然后 `docker compose -p zhifou up -d`；② 确认 `proxy_headers.conf` 已上传到 `/opt/zhifou/nginx/`，且配置里有 `include /opt/zhifou/nginx/proxy_headers.conf;` |
| 5 | **上传图片/扫描件失败**（转圈、413、或直接报错） | ① Nginx 限制太小；② `/opt/zhifou/media` 目录权限不足；③ 磁盘满了 | ① 确认 Nginx 里有 `client_max_body_size 50m;`；② 执行 `chmod -R 777 /opt/zhifou/media`；③ `df -h` 看磁盘 |
| 6 | **导出的 PDF 中文全是方框** | 容器里没有中文字体 | 宿主机执行 `dnf install -y wqy-microhei-fonts wqy-zenhei-fonts`，然后 `cd /opt/zhifou && docker compose -p zhifou restart web`（长期做法是把字体装进镜像） |
| 7 | 容器**一直在 Restarting** | 环境变量缺失或填错（最常见是 `ZF_SECRET_KEY` / `ZF_ALLOWED_HOSTS` 空着） | `cd /opt/zhifou && docker compose -p zhifou logs web` 看最后几行，红字通常是 `RuntimeError: 生产环境必须设置 ZF_ALLOWED_HOSTS` 或 `KeyError: 'ZF_SECRET_KEY'`，补进 `.env` 后 `docker compose -p zhifou up -d` |
| 8 | 网站打不开，显示**宝塔默认页 / Nginx 欢迎页** | 站点配置里的 `server_name` 没改成你的域名，Nginx 没匹配上 | 配置文件里 `server_name` 改成你的域名，**80 段和 443 段各有一处** |
| 9 | 宝塔保存配置时**报 `nginx: [emerg] unknown ...`** | 配置写错，或 `include` 的文件不存在 | 最常见是 `/opt/zhifou/nginx/proxy_headers.conf` 没上传。上传后重试；实在不行把 3 行 `include` 删掉，改为把 `proxy_headers.conf` 里的内容直接粘进每个 `location` 里 |
| 10 | 申请 Let's Encrypt **证书失败** | 域名没解析到本机，或 80 段被 301 拦掉了证书校验 | 先 `ping 你的域名` 确认是本机 IP；再确认 80 段里 `location ^~ /.well-known/acme-challenge/` 写在 `return 301` **之前** |
| 11 | 页面能开，但**取不到数据**（一直在转圈，F12 里 `/api/...` 404） | 请求被前端页面吞掉了，说明 `/api/` 这段 location 没生效 | 确认 443 段里有 `location ^~ /api/ { proxy_pass http://zhifou_backend; ... }`，并且**没有**被写进 `location /` 之后又被覆盖；保存后 `nginx -s reload` |
| 12 | 执行脚本报 **`$'\r': command not found`** | 脚本从 Windows 传上来带了 Windows 换行符 | `sed -i 's/\r$//' /opt/zhifou/scripts/*.sh` |
| 13 | 执行脚本报 **Permission denied** | 文件没有执行权限 | 用 `bash /opt/zhifou/scripts/xxx.sh` 这种方式运行，或 `chmod +x /opt/zhifou/scripts/*.sh` |
| 14 | 服务器很卡 / 构建镜像时进程被杀 | 4G 内存不够 | 停掉宝塔里用不到的 MySQL / PHP（见 1.1）；或临时加 swap：`dd if=/dev/zero of=/swapfile bs=1M count=2048 && chmod 600 /swapfile && mkswap /swapfile && swapon /swapfile` |
| 15 | `/health/` 通但访问域名 400 Bad Request | `ZF_ALLOWED_HOSTS` 和实际访问域名不一致 | `.env` 里改成实际域名（多个用英文逗号隔开，不要带空格、不要带 https://），然后 `docker compose -p zhifou up -d` |
| 16 | 数据库连不上 / migrate 报 authentication failed | `.env` 里的数据库账号密码和 `docker-compose.yml` 里 db 服务的不一致 | 两边都用同一套 `POSTGRES_USER` / `POSTGRES_PASSWORD` / `POSTGRES_DB`；改完需要删库重建（**先备份**） |
| 17 | 502，且 Nginx 错误日志里有 **`(13: Permission denied) while connecting to upstream`** | 系统开了 SELinux，禁止 Nginx 往外连端口 | 执行 `setsebool -P httpd_can_network_connect 1`；想快速验证可临时 `setenforce 0`（重启后失效） |
| 18 | 宝塔保存配置报 **找不到 proxy_headers.conf**，或全部请求都 502 | `/opt/zhifou/nginx/proxy_headers.conf` 没上传，或路径写错 | 把文件传到 `/opt/zhifou/nginx/`；确认配置里 3 行 `include /opt/zhifou/nginx/proxy_headers.conf;` 都在 |
| 19 | **备份里的 media 是空包**，或重启容器后**上传的扫描件/答题卡全没了** | `.env` 里 `ZF_STORAGE_ROOT` 没设成 `/app/media`，文件被写进了容器内部的 `/app/.zf-storage` | `.env` 加 `ZF_STORAGE_ROOT=/app/media` → `cd /opt/zhifou && docker compose -p zhifou up -d`；再用 `docker compose -p zhifou exec web python -c "from apps.media.storage import get_backend; print(get_backend().root)"` 确认输出是 `/app/media` |
| 20 | 批改后页面很慢 / **后台 worker_calc 一直没活干** | `.env` 里 `ZF_TASK_MODE` 不是 `queued`（默认是 inline，重算在网页进程里同步跑） | `.env` 加 `ZF_TASK_MODE=queued` → `cd /opt/zhifou && docker compose -p zhifou up -d`；再用 `docker compose -p zhifou exec web python -c "from apps.analytics.tasks import task_mode, is_queued; print(task_mode(), is_queued())"` 确认输出 `queued True` |
| 21 | 日志里有 **`生产环境仍在使用本地文件存储`** 这条警告 | 单机部署的正常现象，不是故障 | 不用处理。只有当你把文件改存到腾讯云 COS（`ZF_STORAGE_BACKEND=s3`）后这条才会消失 |
| 22 | 敲 `docker compose` 提示 **command not found**，或报 **`name` 字段不认识 / `depends_on` 不认识** | 服务器装的是老版 `docker-compose` v1（带横杠），或者根本没装 compose 插件 | 执行 `dnf install -y docker-compose-plugin`，然后用**带空格**的 `docker compose version` 确认是 v2（见第 1.0 节） |
| 23 | 备份脚本**报错退出**，提示 media 目录是空的 | 数据库里有媒体记录、但磁盘上一个文件都没有 → 文件没写到 `/opt/zhifou/media` | 按第 19 条处理；确认 `ZF_STORAGE_ROOT=/app/media` 并 `up -d` 后重跑备份 |
| 24 | 改了 `.env` 之后**没变化** | 容器只在创建时读一次 `.env`，不会热更新 | 执行 `cd /opt/zhifou && docker compose -p zhifou up -d`（见第 5.8 节） |
| 25 | `curl -sI https://你的域名/static/admin/css/base.css` **不是 200** | 静态目录没挂到宿主机，或没跑 `collectstatic` | `cd /opt/zhifou && docker compose -p zhifou run --rm web python manage.py collectstatic --noinput`，再确认 `/opt/zhifou/staticfiles/admin/css/base.css` 存在、且 Nginx 里 `alias /opt/zhifou/staticfiles/;` 在（见第 4.3 节） |
| 26 | 部署脚本报 **「无法自动检查…★ 不是通过」** | 脚本读不到后端内部状态（接口改名或 web 没在跑） | 这是**警告不是错误**，系统可能仍然是好的 —— 但必须按提示手动敲那条命令确认，不能当成已经验过 |

## 附录 C · Nginx 路由优先级说明（为什么 `/api/` 不会被前端页面吞掉）

Nginx 挑选 `location` 的规则是：**前缀 location 按「最长匹配」胜出，与书写顺序无关**。

- `/static/`、`/health/`、`/api/`、`/admin/`、`/assets/` 都比 `/` 长，
  所以请求 `/api/v1/questions/` 一定命中 `location ^~ /api/`，**永远不会**落到 `location /`。
- 只有上面都不匹配的请求，才会落到最后的 `location / { try_files $uri $uri/ /index.html; }`，
  由前端路由去处理 —— 这正是 `/login`、`/assignments/12`、`/s/<token>` 能直接刷新打开的原因。
- 配置里全部使用 `^~` 前缀匹配，**不使用正则 location**，避免正则反过来抢走这些前缀。
- `proxy_pass http://zhifou_backend;` **结尾没有斜杠**，所以 `/api/` 前缀会原样传给后端，
  后端收到的还是 `/api/v1/questions/`，不会被改写成 `/v1/questions/`。

## 附录 D · 为什么 Nginx 里没有 `/media/`（安全说明）

> **这是有意关闭的安全设置，请不要手动打开。**
> 配置里这一段被**整段注释掉了**（不是漏配，也不是删掉）。
> 为什么留注释而不留空白：空白会被以后维护的人从别的教程里抄一段回来重新填上，
> 留一段写着「这里有一段，为什么不能打开」的注释更安全。Nginx 不解析注释行，安全性等价。

部署方案最初规划过一段 `location ^~ /media/ { alias /opt/zhifou/media/; }`。
核对代码之后，这一段被**注释关闭**，原因：

1. 知否全站**没有任何代码会生成 `/media/` 开头的网址**。
   `settings/base.py` 里定义了 `MEDIA_URL="/media/"`，但全仓库**零处引用**；
   本地存储的 `signed_url()` 返回的是 `file://`，不会产生 HTTP 地址。
   也就是说这段配置**平时根本用不上**。
2. 但它一旦加上，就等价于**「任何人猜到文件路径就能免登录下载」**——
   这个目录里不只是题目配图，**还有学生的答题卡照片和扫描件**，属于实打实的越权泄露。
3. 真正取字节的接口是 `/api/v1/media/assets/{id}/content/`，
   它**要登录、还要校验归属机构**，这才是设计上认可的读取方式。

所以在 `nginx/zhifou.conf` 里，这一段以**注释形式保留**，块里写清了三件事：
它是有意关闭的安全设置、正确的读取路径是 `/api/v1/media/assets/{id}/content/`（要登录 + 校验归属）、
以及为什么要关。文件头部那段路由总览里**没有**把 `/media/` 列为标准目录，免得看起来像标配。

**★ 万一将来真的必须重新启用**（只有后端改成「对外直接吐 `/media/xxx.png`」这一种情况）：

1. **必须**把缓存头改成 `add_header Cache-Control "private, no-store";`
2. **绝不能**关掉 `access_log`。原来那几行里最坏的一条就是 `access_log off` ——
   一旦口子真的被人用过，**查都查不出来**。注释里保留的 `access_log off` 是错误示范，别照抄。
3. 注释块里已经写好了一份「启用时的正确写法」，照那份改。

其它注意事项：

- **请不要**从别的教程里抄一段 `location /media/` 加进来。
- 如果以后改成腾讯云 COS / 对象存储（`ZF_STORAGE_BACKEND=s3`），
  字节不再由本机提供，这个顾虑自然消失，这段可以直接删掉。
- 每次改过 Nginx 配置，请回到第 4.2 节做一次「反向验收」，
  确认 `curl -sI https://你的域名/media/<真实图片名>` 的 `content-type` 是 `text/html`
  而不是 `image/*`。
